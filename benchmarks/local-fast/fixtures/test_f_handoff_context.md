# 项目记录：eye-tracking 数据管线重建（用于 handoff 压缩测试）

## Goal

把眼球追踪实验的数据处理管线从一次性脚本重建成可重复运行的批处理系统。
原始需求来自实验室：每天产生约 40 组被试数据，每组包含 2 路红外摄像机视频、
1 路屏幕录制、以及 4 个校准文件。旧流程是研究生手动运行三段 Python 脚本，
经常因为路径写错或中间文件残留导致结果不一致，同一批数据不同人跑出来的
注视点数量能差 3% 到 7%，无法用于论文。

新的目标是：一条命令处理一整天的数据；所有中间产物有版本化的目录结构；
任何一步失败都能从断点恢复；最终输出固定格式的 CSV 加一份质量报告。
验收标准是同一批输入重复运行三次，输出完全一致（逐字节比较）。

## Current state

管线主体已经能跑通，但还没达到"逐字节一致"的验收标准。
目前状态是：预处理阶段稳定，注视点检测阶段在约 15% 的被试上会出现
随机波动，波动集中在眨眼密集的片段。质量报告已经能生成，
包含每个被试的有效采样率、剔除时长、以及注视点统计。

代码放在 `src/eyetrack/` 下，入口是 `src/eyetrack/cli.py`，
用 `python -m eyetrack.cli run --date 2026-09-20` 触发。
配置在 `config/pipeline.yaml`，其中定义了每个阶段的参数和输出路径模板。

数据集本身不进入 git，放在 `/data/eyetrack/raw/` 下，
以 `YYYY-MM-DD/<subject_id>/` 组织。中间产物写在 `/data/eyetrack/work/`，
最终结果在 `/data/eyetrack/out/`。

## Completed

预处理阶段已经完成并且稳定。具体包括：

`src/eyetrack/preprocess/sync.py` 实现了视频与屏幕录制的时间戳对齐，
用屏幕录制的帧计数作为主时钟，容差设为 16 毫秒（一帧）。
对齐失败的样本会写入 `work/<subject>/sync_fail.json` 而不是直接抛出异常。

`src/eyetrack/preprocess/calibrate.py` 解析四个校准文件，
把屏幕坐标映射到注视向量。这里踩过一个坑：实验室的两台设备
导出的校准文件坐标系不一致，一台是左上原点，另一台是左下原点。
现在通过读取文件头部的 `origin` 字段自动判别，
如果是 `bottom-left` 就在加载时翻转 y 轴。

`src/eyetrack/preprocess/face.py` 用 MediaPipe 做面部关键点检测，
输出眼睛区域裁剪后的视频片段。为了加速，这一段被改成按需解码，
不再一次性把整个视频读进内存——之前的版本在 40 组数据上会吃掉 30GB 内存。

批处理调度用 `src/eyetrack/scheduler.py`，基于进程池，
每个被试一个任务，失败自动重试两次，重试前清理该被试的 work 目录。
日志写到 `logs/<date>/pipeline.log`，结构化 JSON 格式。

## Failed

第一版注视点检测尝试直接用 I-DT 算法（dispersion-threshold identification），
阈值凭经验设为 1 度视角、最小持续 100 毫秒。问题是这个方法对采样率很敏感，
设备实际采样率在 60Hz 到 200Hz 之间浮动（受 USB 带宽影响），
固定时间阈值在不同被试上等价于不同的采样点数，导致结果不可比。
这一版被放弃，代码还留在 `src/eyetrack/detect/idt_legacy.py`，没有删除。

第二版改用 I-VT（velocity-threshold），把速度阈值归一化到视角每秒，
这样就和采样率解耦了。效果明显好转，但在眨眼密集片段仍有波动。
追查后发现是平滑滤波器的窗口长度是固定的 5 帧，
在高采样率下相当于极短时间窗，在低采样率下又过长。
改成按时间定义窗口（相当于 20 毫秒）之后波动下降到 15% 的被试。

还有一个失败的尝试是引入 GPU 加速。原本打算把面部检测放到
CUDA 上跑，但 MediaPipe 在这个环境下的 GPU 路径和 Triton 推理服务冲突，
而且单组数据的面部检测本身只需要 12 秒，加速收益不足以抵偿复杂度，
所以明确放弃了，这一段记录在 `docs/decisions/0003-no-gpu-face-detect.md`。

- `tests/test_sync.py`、`tests/test_calibrate.py`、`tests/test_ivt.py`

## Important decisions

决策一：中间产物一律使用 Parquet 而不是 CSV。原因是中间数据有几十列且
包含大量浮点，CSV 的文本往返会引入精度损失，而我们要求逐字节可复现。
Parquet 写入时固定了 schema 和压缩级别，这一点记录在
`docs/decisions/0001-parquet-intermediate.md`。

决策二：不使用 GPU。除了上面提到的收益不足，还有一个原因是
实验室的机器是共享的，GPU 经常被其他人的训练任务占用，
把管线绑在 GPU 上会让整条链路变得不可预测。

决策三：所有随机性必须显式播种。管线里任何涉及随机的步骤
（主要是数据增强和采样）都从 `config/pipeline.yaml` 的 `seed` 字段取值，
默认 20260401。这是"逐字节一致"验收标准的前提。

决策四：不使用全局状态。旧脚本用模块级变量缓存配置，
导致同一个进程里跑第二个被试时会带上第一个被试的参数。
现在配置通过显式参数传递，`cli.py` 是唯一读取配置文件的地方。

## Tests

`tests/test_sync.py` 覆盖了正常对齐、容差边界、以及对齐失败的三种情况，
用三个小的合成视频夹具，全部通过。

`tests/test_calibrate.py` 覆盖了两种坐标系、缺失字段、以及
坐标值超出屏幕范围的情况。目前有一个用例是 skip 状态：
左下原点且带旋转的校准文件没有真实样本，无法构造可信的期望值。

`tests/test_ivt.py` 覆盖速度阈值的边界，以及眨眼片段被正确剔除。
这个测试目前是**不稳定的**，在 CI 上大约每 20 次失败一次，
怀疑和浮点累加顺序有关（进程池的返回顺序不保证），但还没确认。

整体覆盖率是 71%，未覆盖的主要是 `report/quality.py` 的格式化分支。

## Open questions

1. 逐字节一致的失败到底来自哪里？目前怀疑两处：一是
   `detect/ivt.py` 里对注视点做排序时用了不稳定的排序键
   （只有时间戳，没有次级键），二是 `scheduler.py` 收集结果时
   按完成顺序而不是按被试 ID 顺序写文件。这两个都还没有验证。
2. `test_ivt.py` 的偶发失败是否和上面同源？如果是，修好排序键
   可能同时解决两个问题。
3. 左下原点带旋转的校准文件是否需要支持？实验室说这种设备
   下个月可能到货，但没有明确。如果支持，`calibrate.py` 需要
   引入旋转矩阵，工作量大约两天。
4. 质量报告里的"有效采样率"定义是否合理？目前定义为
   剔除眨眼和丢失帧之后的采样点数除以理论采样点数。
   导师认为应该按时间加权，但这会让报告更难解释。
5. 是否需要保留 `idt_legacy.py`？现在没有任何代码引用它，
   但论文的方法对比章节可能要引用旧结果。

## Next step

优先验证第 1 个问题。具体做法：在 `scheduler.py` 的收集阶段
改为按被试 ID 排序后写文件，给 `detect/ivt.py` 的排序键加上
次级键（帧索引），然后对同一批 5 个被试连续运行三次并做
逐字节比较。如果仍然不一致，就在每一步的 Parquet 输出上
计算哈希并做逐步对比，定位是哪一阶段首次出现差异。

这一步完成后，如果验收标准达成，就把
`tests/test_ivt.py` 的不稳定问题一并复查。

## 附：历史会话记录节选（上下文噪声，用于检验压缩能力）

以下内容来自过去两周的开发对话，包含重复讨论和已废弃的方案，
压缩时应当被归纳而不是逐条照搬。

我们一开始讨论过是不是要换成 Snakemake 或者 Nextflow 这样的工作流引擎。
支持的理由是断点恢复、依赖管理、并行调度这些都是现成的，
不用自己写。反对的理由是团队只有两个人熟悉 Python，
引入新工具的学习成本和调试成本都不低，而且我们的依赖图其实很简单，
就是一条链加一个扇出。最后决定自己写调度器，
但借鉴了 Snakemake 的一些想法，比如把每个阶段的输出声明成目标、
按文件是否存在判断是否需要重跑。这个讨论持续了三天，
中间还试过用 DVC 管理数据版本，但 DVC 对二进制大文件的支持
在共享文件系统上有一些问题，放弃了。

关于坐标系的问题又讨论过一次。有人提议干脆把所有数据
预处理成统一坐标系再存一份，这样下游不用关心。
但这样会让原始数据和处理后数据混淆，而且磁盘占用翻倍，
所以还是保持读时转换。

关于是否需要 EyeLink 的原生解析库，讨论后确认不需要，
因为实验室现在用的是 Tobii 设备，EyeLink 是另一条线的历史数据，
不在本次范围内。但如果以后要处理，`preprocess/` 下需要新增一个模块。

性能方面，全量 40 组数据端到端跑完需要约 55 分钟，
瓶颈在面部检测（约 12 秒/组，串行占大头）。有人提议
把进程池从 4 提到 8，实测提升有限而且内存峰值上升到
18GB，接近机器上限（24GB），所以维持 4。

关于日志格式，早期用纯文本，后来改成 JSON，
因为要接入监控。但 JSON 日志在终端里不容易读，
所以加了一个 `--human-logs` 开关，内部用同样的结构化数据，
只是渲染成人类可读的格式。

还有一次讨论是关于要不要写单元测试。有人觉得数据处理
管线主要靠端到端验证，单元测试价值不大。最终决定还是写，
因为端到端失败时无法定位是哪个环节的问题，
而这次"逐字节一致"的排查正好证明了单元测试的必要性。

## 附：接口与数据结构细节

`cli.py` 暴露的命令行接口如下。`run` 子命令接受 `--date`（必填，格式 YYYY-MM-DD）、
`--subjects`（可选，逗号分隔的被试 ID，缺省表示当天全部）、`--stages`
（可选，限定只跑某几个阶段，例如 `preprocess,detect`）、`--force`
（忽略已有的中间产物强制重跑）、`--resume`（从最后一个完整阶段继续）。
另有 `verify` 子命令，接受 `--date` 和 `--repeat N`，
对同一天数据连续运行 N 次并逐字节比较输出，这是我们验收"可复现"的标准工具。
还有 `report` 子命令，只根据已有的中间产物重新生成质量报告，不重跑计算。

中间产物的目录约定是 `work/<date>/<subject_id>/<stage>/`，
每个 stage 目录下至少包含 `data.parquet` 和 `meta.json`。
`meta.json` 记录该阶段的输入文件哈希、参数快照、开始与结束时间、
以及处理过的帧数。这个文件是断点恢复的依据：
如果 `meta.json` 存在且其中记录的参数快照与当前配置一致，
就认为该阶段已完成，除非显式传 `--force`。

`config/pipeline.yaml` 的顶层字段包括 `seed`、`paths`、
`preprocess`、`detect`、`report` 四块。
`preprocess` 下细分为 `sync.tolerance_ms`（默认 16）、
`calibrate.origin_override`（默认 null，用于强制指定坐标系，
应对文件头缺失的旧数据）、`face.model_path`（MediaPipe 模型文件路径）、
`face.min_confidence`（默认 0.5）。
`detect` 下细分为 `method`（当前固定为 ivt）、
`ivt.velocity_threshold_deg_per_s`（默认 30）、
`ivt.smoothing_window_ms`（默认 20）、
`ivt.min_fixation_ms`（默认 100）、
`ivt.blink_velocity_deg_per_s`（默认 300，超过这个速度判为眨眼）。
`report` 下细分为 `valid_sample_rate.min`（低于此值标记该被试为低质量）、
`output_format`（当前为 csv，可选 parquet）。

## 附：已知的环境问题

开发机上装了较新的 Python 3.13，MediaPipe 的官方 wheel 对 3.13 的支持
在最初并不完整，我们是靠社区构建的 wheel 才装上。这一点需要记录，
因为如果换机器重建环境，可能会卡在这里。长远来看应该把 Python 版本
固定在 3.11 或者 3.12，MediaPipe 对这两个版本的支持是稳定的。

另外，共享文件系统在大量小文件写入时性能很差。中间产物如果切成
很碎的小文件，光元数据操作就要花掉几分钟。这也是选择
"每个阶段一个大 parquet"而不是"每帧一个文件"的原因之一。

其中 `read_csv_safe` 已经被弃用但仍然被 `report/quality.py` 引用，
这是一个待清理的耦合。清理计划是先把 `quality.py` 改用 parquet 读取，

需要同时更新 `tests/test_report.py`（该文件目前只有两个用例）。

文档方面，`docs/decisions/` 下的三份记录都写得比较完整，
但 `README.md` 已经落后于代码，其中描述的还是第一版 IDT 算法，
而且用法示例里的命令参数（`--day`）已经改名成 `--date`，
这是一个已知会误导新人的问题，优先级中等。

依赖管理用 `requirements.txt`，没有锁版本。这在实验室环境里
导致过一次事故：某次升级 numpy 之后，浮点累加的结果出现极微小差异，
虽然不是"逐字节一致"失败的根因（那次失败在引入 numpy 升级之前就存在），
但确实让排查过程变得更混乱。现在的做法是记录当时的版本号到
`docs/env-snapshot.txt`，但不强制锁定。是否引入 pip-tools 或者 uv
来做真正的锁定，还没有决定。

磁盘占用方面，`/data/eyetrack/work/` 会持续增长，目前一天约 40GB。
保留策略是手工清理，没有自动过期机制。如果需要长期跑，
应该加一个按天数的清理脚本，但要注意不能删掉最近一次
用于对比的中间产物，否则逐字节比较就没有基准了。

## 附：质量报告字段说明

`report/quality.py` 输出的报告是一张被试级的表，
每一行对应一个被试，列包括：`subject_id`、`date`、
`total_frames`（原始帧数）、`valid_frames`（通过质量检查的帧数）、
`valid_sample_rate`（前者除以后者）、`blink_frames`、
`lost_frames`（面部检测失败的帧）、`mean_confidence`
（面部检测置信度均值）、`gaze_samples`（输出的注视点样本数）、
`fixation_count`、`mean_fixation_ms`、`median_fixation_ms`、
`excluded_duration_ms`、以及 `quality_flag`。

`quality_flag` 的取值逻辑是：如果 `valid_sample_rate` 低于
配置里的 `valid_sample_rate.min`（默认 0.6）就标为 `low`；
如果 `lost_frames` 占比超过 0.3 标为 `unstable`；
两者都不满足则为 `ok`。这个标记目前只用于人工筛查，
不会自动剔除被试，因为实验设计上是否剔除应该由研究者决定，
而不是由管线决定。这一点在组会上明确过。

报告同时输出一个汇总段落，包含当天被试数、
被标记为低质量的数量、以及全体的平均有效采样率。
汇总段落会被写进 `out/<date>/summary.txt`，
方便直接贴进实验记录。

## 附：性能剖析记录

对一天 40 组数据做过一次粗略的阶段耗时剖析，结果是：
同步对齐平均 3.2 秒/组，校准解析 0.4 秒/组，
面部检测与眼区裁剪 12.1 秒/组，注视点检测 1.8 秒/组，
质量报告生成 0.6 秒/组。总计约 18.1 秒/组，
40 组串行需要约 12 分钟，但实测端到端是 55 分钟，
差异来自文件系统读取——原始视频总大小约 180GB，
从共享存储读一遍就要三十多分钟。这说明当前真正的瓶颈
不是计算而是 I/O，如果要进一步优化，应该先考虑
把原始数据复制到本地 SSD，或者改成按需读取视频片段
而不是整段解码。这一结论还没有写成正式文档。

## 附：一次失败的重构尝试

中途尝试把整条管线改成基于文件哈希的增量执行：
每个阶段计算输入的哈希，如果哈希没变就跳过。
想法是好的，但实现时踩了一个坑——视频文件的哈希
在有些情况下会变化，因为共享存储上某些文件的
修改时间戳会被同步工具改写，而我们最初的哈希实现
把修改时间也纳入了计算。结果导致每次都判定为"已变更"，
增量执行完全失效，跑一遍的时间和全量一样。
修复方式是只对文件内容做哈希，忽略元数据。
但这个修复之后又发现新问题：哈希 180GB 的视频本身
就要花二十多分钟，比直接跑一遍还慢。
最终这个方向被放弃，改为保留 `--resume` 这种
基于阶段完成标记的粗粒度恢复。

## 附：数据格式规范草案

原始数据目录的结构经过一次调整，最终确定如下。
根目录下按日期分目录，日期目录下按被试分目录，
被试目录下直接放该被试的原始文件，不再有更深的层级。
这种扁平结构是为了避免路径过长——Windows 的路径长度限制
在共享存储映射到网络驱动器时会先触发，之前有过一次
因为路径超过 260 字符导致写入失败的问题。

每个被试目录下固定包含以下文件。`eye_left.mp4` 和
`eye_right.mp4` 是两路红外摄像机视频，H.264 编码，
分辨率 640x480，标称 200fps 但实际帧率浮动。
`screen.mp4` 是屏幕录制，H.264，分辨率 1920x1080，60fps 恒定。
`calib_1.json` 到 `calib_4.json` 是四个校准点文件，
每个文件包含 `origin`（坐标系原点，取值为 `top-left` 或
`bottom-left`）、`screen_size`（两元素数组）、
`points`（校准点数组，每个点含 `screen_xy` 和 `gaze_xy`）、
以及 `timestamp_ms`。`session.json` 记录会话元数据，
包含 `subject_id`、`device_id`、`start_time`（ISO 8601）、
`sample_rate_hz`（标称采样率）、以及可选的 `notes`。
`events.csv` 是可选的实验事件表，记录刺激呈现和按键反应，
列为 `timestamp_ms`、`event_type`、`payload`。

设备有两台，`device_id` 分别是 `ET-A` 和 `ET-B`。
`ET-A` 的校准文件使用左上原点，`ET-B` 使用左下原点，
这是前面提到坐标系差异的来源。两台设备的
`sample_rate_hz` 标称值都是 200，但 `ET-B` 在实际测量中
因为 USB 带宽争用更常掉到 60 到 120 之间。
`ET-B` 还有一个小特性：它的 `calib_4.json`
有时会延迟写入，如果处理时正好读到半个文件，
JSON 解析会失败。目前的处理方式是重试三次，
间隔 500 毫秒，仍失败才标记该被试为校准错误。

输出格式方面，最终的注视点 CSV 包含这些列：
`subject_id`、`date`、`frame_index`、`timestamp_ms`、
`gaze_x`、`gaze_y`（屏幕坐标，像素）、
`gaze_angle_x`、`gaze_angle_y`（视角，度）、
`fixation_id`（整数，同一注视点内相同，-1 表示不属于任何注视点）、
`is_blink`（布尔）、`confidence`（浮点）。
文件使用 UTF-8 无 BOM 编码，行尾统一为 LF，
浮点数保留六位小数——这两条都是为了满足逐字节可复现的要求。
排序规则是先按 `subject_id` 升序，再按 `frame_index` 升序，
这是一个全序，不存在并列，因此不依赖排序算法的稳定性。

## 附：与导师的两次同步记录

第一次同步在项目第三周。导师提出的主要意见是
质量报告不应该只给数字，还应该能直接看出问题被试。
我们当时的报告只有汇总统计，确实需要人工翻表格找异常。
根据这个意见加了 `quality_flag` 列，但导师又提出
标记逻辑的阈值应该有实验依据而不是拍脑袋。
这一点暂时无法完全满足，因为目前还没有积累到
足够多的标注样本，只能先用文献里的常见取值，
并在报告里注明阈值来源。这个折中方案导师接受了。

第二次同步在第五周，主要讨论坐标系问题会不会
影响跨设备的对比分析。结论是会影响，因为
即使翻转了 y 轴，两台的镜头畸变模型也不一样，
严格来说需要分别标定。但实验室的历史数据
本来就没有做畸变校正，为了和历史结果可比，
新数据也暂时不做校正，只在文档里记录这个局限。
如果以后要发方法学论文，这一块需要重新处理。

导师还提到希望能有一个"只跑一个被试"的快速调试模式。
这个已经通过 `--subjects` 参数实现了，
另外 `--stages` 参数可以只跑指定阶段，
两者组合起来可以在十秒内验证一个被试的预处理结果。
